Heat Meds app map

A take-home guide: what the pieces are, one action traced through the code, where to start a change, and a practice worth reusing. Built from the code at commit c9c2296 on 2026-09-30. It is a snapshot and can drift as the code changes.

What the app is

Three static pages with no server of their own: index.html (entry), plan.html (the printable plan), and evidence.html (the 300-medicine results). Everything runs in the browser from plain JavaScript modules in src/.

  • Name lookup. The National Library of Medicine's RxNorm turns what is on the bottle into ingredients; RxClass gives each ingredient its drug-class code.
  • Forecast. A bundled Census ZIP file gives coordinates; the National Weather Service HeatRisk service gives seven days of heat risk, or an honest note when it cannot.
  • Rules engine. src/rules.js matches classes against data/cdc-rules.json, the hand-checked CDC table. Every card's words come from that file, with the exact CDC quote.
  • Evidence run. scripts/run-evidence.mjs pushes 300 real prescriptions through the same modules and writes the numbers the Evidence page shows.

The route reference route

Three stops, in the order the action runs. Open each file and search for the quoted text. This route was not toured live in the session; it is here to use when you come back to the code.

1Name to ingredients

src/rxnorm.js, search export async function resolveMedicine; then src/rxclass.js, search export async function classifyMedicine

normalizeName strips dose and form words, so "Lasix 40 mg" becomes "lasix". An exact RxNorm match resolves; anything approximate comes back as a "did you mean" that the person must tap, so the app never guesses. RxClass then adds the drug-class code (furosemide gets C03CA, a loop diuretic), keeping only rows for the ingredient itself.

2ZIP to a heat week, or an honest note

src/heatrisk.js, search export function insideForecastArea, export async function forecastFor, and export function chooseWeek

Points outside the contiguous United States are "not available" before any call is made, and the service's own "not covered" error counts the same way. Only a real outage falls back to the saved Phoenix heat wave, and chooseWeek labels it. This is the stop to read if a place ever shows the wrong heat.

3Medicines and week to the plan

src/rules.js, search export function evaluate and function summarize; drawn by src/plan-render.js, search export function renderPlanSections

evaluate is pure: no network, no page. It builds cards from data/cdc-rules.json only, adds one combination warning at most, and lets the weather change nothing but the summary and each card's "this week" line. The same function runs in the browser, the tests, and the evidence run, which is why the Evidence page describes the code the site runs.

A practice to reuse

For every "must never" requirement, test it with a real input from the edge of coverage, and make the test prove it can fail.

The decision. The product requirements separated two cases on purpose: a ZIP outside the forecast area shows a note, and only a service outage shows labeled saved data (devpost/prd.md, "Entering the ZIP and getting the forecast").

The evidence. Every test passed on Phoenix fixtures. A real Honolulu ZIP, tried during final review, showed the Phoenix heat wave with "Wed is an Extreme heat risk day where you live." The service reports "not covered" as an error inside a normal reply, which no fixture contained. Because the requirement was precise, the failure was obvious, and it became two sharper rules and a test (test/forecast-modes.test.mjs, commit c9c2296). While writing that test, a guard check showed the first version of the "never say today" pattern could not fail at all. The fix was a test that runs the pattern against a known-bad sentence.

On the next project. Next to each happy-path example, add the input most likely to be different from what you built on: another region, an empty list, a service error. Beside every "never" check, assert that it catches one sentence it is meant to catch.

The same pattern, found by the 300-medicine run

Hand-picked examples all resolved to drug classes. The 300 most-prescribed medicines did not: olmesartan (a blood pressure medicine) and isosorbide (a nitrate) were missed because RxClass files their class codes under a precise form, such as olmesartan medoxomil. The fix is async function classesViaPreciseForms in src/rxclass.js (commit ba97e9d). Real outside data exposed what the fixtures could not.
